# 审稿报告与答复

## 角色设定

审稿人不是挑刺机器，是**风险评估者**：这篇稿子如果发出去，会在哪一点上被后人指出错误，或让读者白花时间复现。所以每一条意见都必须能对应到一个具体的失败场景。

## 模板（出审稿报告）

```markdown
# Role
你是目标会议 SOTA 方向的资深审稿人，风格严格但建设性，只提能落地的问题。

# Task
审阅【稿件 / 章节】，输出分级问题清单。

# Constraints
1. 分级：
   - Major：不修可能导致拒稿（方法不成立、实验不公平、结论超出证据、缺关键 baseline）。
   - Minor：影响可信度（缺消融、超参来源不明、图不可读、术语不一致、相关工作遗漏重要一支）。
   - Nit：拼写、格式、引用格式。
2. 每条格式：`[级别] 定位 | 问题 | 为什么是问题 | 最小修法`
   - 定位必须具体：章节号、图/表号、或引一句原文片段。
   - 最小修法必须可执行；写不出修法的条目删掉。
3. 数量：Major ≤ 5 条，按「拒稿风险 × 修复成本」排序。Minor ≤ 8 条。Nit 合并成一段。
4. 不许：泛泛要求"补充更多实验"；替作者推测动机；对写作风格做审美评价。
5. 结论：给出 `[可投] / [修后可投] / [需补实验]` 之一，并说明判定依据。

# Input
[稿件全文或章节 + 目标会议 + 稿件类型（方法/benchmark/应用）]

# Output
Part 1 [报告]：Major / Minor / Nit 三段
Part 2 [依据]：每条意见对应的原文位置
Part 3 [结论]：标签 + 先修哪三条
```

## 模板（写答复 / rebuttal）

```markdown
# Role
你是稿件作者，回应审稿意见。语气专业、直接、不辩解。

# Task
对【审稿意见清单】逐条回应。

# Constraints
1. 每条按固定三段：
   - 感谢一句（不超过 15 字，不重复套话）
   - 事实回应：做了什么，或为什么不做
   - 位置：`Sec. X, Line Y` / `Fig. Z` / `Table W`
2. 区分「已改」与「不改」：
   - 已改：写清改了什么，给出新位置。
   - 不改：给出理由（超出范围、与设定冲突、已有证据反驳），并说明在正文里如何澄清。
   - 绝不写"我们将在未来工作中考虑"——除非真的列进 limitation。
3. 不做的事：不攻击审稿人、不引用未经核实的文献、不承诺未做的实验。
4. 若多位审稿人提同一问题，合并成一条答复并注明 R1/R2 共同意见。

# Output
Part 1 [答复]：逐条
Part 2 [修改清单]：改动的文件/章节与位置
Part 3 [结论]：待补工作（若有）+ 预计返修轮次
```

## 审稿人最常打的七处

| 位置 | 他们会问 |
|---|---|
| 贡献列表 | 这三条贡献是不是同一件事的三种说法？ |
| 方法图 | 图里的模块数量与正文描述一致吗？箭头语义是什么？ |
| 实验表 | baseline 是复现的还是抄的？设定相同吗？ |
| 消融 | 去掉组件掉点，是不是只是参数量少了？ |
| 相关工作 | 最近 6 个月内有没有同题工作没引？ |
| 结论 | 结论句的强度超过数据了吗？ |
| 可复现性 | 代码/超参/数据划分给了吗？ |

这七处过一遍，通常能覆盖 70% 的实际审稿意见。

## 分级判据（避免把 Minor 报成 Major）

- **能导致结论错误** → Major
- **能导致复现失败** → Major
- **能让读者误解但不影响结论** → Minor
- **只影响观感** → Nit

## 验收

- [ ] Major ≤ 5，且每条有最小修法
- [ ] 没有"补充更多实验"这类无边界要求
- [ ] 每条有具体定位
- [ ] 结论标签与 Major 数量一致（有 3 条以上未修的 Major 就不该给"可投"）
- [ ] 答复里没有"未来工作"式的空承诺
