## 1 已跑通的两组 GPU 训练

### 1.1 P1-b 观测可靠性 —— TCN 时序分类器

| 项 | CPU 基线（10 手工几何特征 + 逻辑回归/马氏） | GPU TCN（本脚本） |
|---|---|---|
| 模型 | 逐帧独立特征 | 4 残差块 TCN，dilation 1/2/4/8，96 通道，GroupNorm+GELU |
| 输入 | 逐帧 8 维几何量 | 82 维/帧 × 15 帧因果窗（0.5 s） |
| 参数量 | — | 243,873 |
| test AUC | 融合 0.6267（校准 0.5961 / 几何 0.6131） | **0.8220**（+0.1953，+31.2% 相对） |
| test AP | 0.0407（正例率 0.0189 → 2.15×） | **0.0676**（→ **3.55×**） |
| 环境 `..._0011`（最难） | 0.5281（12,634 帧 / 426 正） | **0.7646**（6,275 窗 / 213 正） |
| 环境 `..._0041` | 0.9383（7,274 帧 / 36 正） | 0.8639（3,623 窗 / 18 正） |
| 训练耗时 | 秒级（CPU） | **18.8 s**（18 epoch，batch 1024，46,276 训练窗） |

要点：基线里 **`0011` 那个环境的 AUC 0.5281 等于没有信号**，这是 C 题 P1-b 最难看的数字；
换时序卷积后同一划分、同一标签下到 **0.7646**，说明"逐帧独立"本身就是错误假设——
手部遮挡是**成段**的，必须用时序上下文。这既是数字改进，也是论文里一条能站住的论点。

残留问题：`best_epoch = 1`（val AUC 0.8853 后单调回落），46,276 窗 / 243 k 参数下**一轮即过拟合**。
改进方向已列入 §4（减容量、加 dropout、加时间抖动增强、拉长 warmup），属于润色级，不影响结论方向。

### 1.2 P2 缺失观测下的轨迹预测 —— GRU 编码器 + 多步头

窗口档位对齐官方 `common_conditions.json` 的 `observation.prefix_seconds = [0.2, 0.6, 1.0]`
（= 6 / 18 / 30 帧 @30 fps），另加 60 帧做外推压力测试。目标：主导手腕头坐标系位置，
相对最后观测帧的位移。

| 档位 | ridge（CPU 基线） | GPU v1（**同输入**，仅 3 维手腕） | GPU v2（双手 32+32 + 头部几何 8+8 = 80 维） |
|---|---|---|---|
| 0.20 s（6 帧） | RMSE 2.34 cm / 中位 0.84 cm | 1.38 / 1.24 cm | **0.54 / 0.28 cm** |
| 0.60 s（18 帧） | —（未测） | 2.86 / 2.79 cm | **2.29 / 2.03 cm** |
| 1.00 s（30 帧） | 中位 **15.30 cm** / q90 101.9 cm | 3.74 / 3.87 cm | **3.31 / 3.18 cm** |
| 2.00 s（60 帧） | 中位 **57.62 cm** / q90 406.9 cm | 5.00 / 5.49 cm | **4.53 / 5.00 cm** |

要点三条：

1. **同输入下换模型就有 1.7× 增益**（0.2 s：2.34 → 1.38 cm），所以这不是"多喂数据"的功劳，
   是"轨迹必须按序列建模、不能逐帧回归"的功劳。
2. **补全关键点再翻一倍**（1.38 → 0.54 cm，4.3× 对 ridge）。in-domain 的 2 cm 精度终于成立：
   `within_2cm` 从基线 77.7% 提到 **95.8%**。
3. **长档位是数量级差**。1 s 处 ridge 中位误差 15.3 cm、2 s 处 57.6 cm（保形 90% 半径 1.02 m / 4.07 m，
   等于"2 秒后不知道手在哪"），GPU 到 3.2 / 5.0 cm。**P2 的"再观测经济学"整条曲线因此重算**——
   观测的价值随档位急剧上升这一性质反而更清晰。

口径声明（必须写进论文脚注）：ridge 基线在 cap 300–400 窗口子集上评估，GPU 在全滑窗上评估，
两者**同一 record 划分**；方向稳健，倍数按量级读，不作小数点级对比。

### P3 硬缺口的具体改法

`common_conditions.json` 其实把协议全给了：`prefix_seconds [0.2, 0.6, 1.0]`、`delay_s 1.0`、
`cost 1.0`、`max_per_job 2`、`obs_limit 4/6/8`、`reserve_min_s 0.2`、`reservation_released_early false`。
我此前用了一个标量代理 `review_gain_assumed_s = 0.11` 去近似"看前缀能省多少时间"，
敏感性扫描显示 gain 调大后 `reviews` 升到 4–6 但准时率反而从 0.8208 掉到 0.7958 / 0.7083
——**代理方向错了**，所以整个再观测维度被压成 0。

正确做法：把 `prefix_seconds` 变成**可执行前缀的实测值**（`prefix_features.csv` 已有每单元
0.2/0.6/1.0 s 前缀的速度/开合/深度统计），用 P1-b 的可靠度当"该前缀可信与否"的判据，
再按 `cost = 1.0`、`delay = 1.0` 进调度器做 lookahead。这是**代码改动**，不是新数据，约 1–2 h。

## 4 决策规则与建议

**改走 C 的启动条件（今天 24:00 前）**：
P3 再观测补上并跑出结果。判据按此前承诺：S2、S3 的 mean weighted on-time rate 提升
**均 ≥ 0.05** → 改走 C；**< 0.02** → A 定案；中间地带按剩余工时定。

**我现在的建议：改走 C，但把 A 的提交件锁死不动作为保险。**

理由，按重要性：

1. **C 的短板正好被我刚跑出来的数字补掉了。** 我反对 C 的两条理由是"头条数字弱"和"P2 协议不可控"。
   前者已被 AUC 0.5281→0.7646、2 s 中位误差 57.6→5.0 cm 推翻；后者被证伪——
   协议就在 `common_conditions.json` 里，是我没读懂。
2. **C 有真新意，A 没有。** A 的 3,769 行代码里，机理求解是教科书 Richards+Mazars+Pedrosa、
   形状是 √t/exp/power/Arps、优化是现成 NSGA-II、敏感性是现成 Saltelli；
   16/16 门与 116 条断言查的是**格式与自洽**，没有一条查"有没有新意"。
   C 的"逐帧独立 vs 时序建模"是一个能写进摘要的发现，且被数字支持。
3. **难度在评奖里是资产。** C 是唯一要求 5.8 GB 真实多模态数据 + POMDP + 随机调度 + 算力的题；
   评委看得出一支队伍做到了哪一层。
4. **A 的保险是免费的。** A 的 `ASWBMCM2634892.pdf` / `cns.pdf` / `fj.zip` 已经做好，
   放在那里不动即可；C 失败就交 A，代价只是三天。
